- (decision) AD-1 Paradigm: Actor model with pipes-and-filters inner loop. Each Agent is an autonomous OS process owning a linear capture→policy→action pipeline internally. The Orchestrator and GPU Inference Server are separate actors. All cross-process communication is ZeroMQ. Binds: all components. Prevents: shared mutable state across agents; GIL contention; non-deterministic cross-agent coupling.
- (decision) AD-2 GPU Inference Server (Option B): One dedicated process owns all GPU calls. Batches frames from both Agent windows each tick using Ultralytics YOLOv8-nano. Returns detections to each Agent via ZeroMQ. Agents are CPU-only processes (capture, OCR, policy, action). Binds: WL Agent, PP Agent, GPU Inference Server. Prevents: non-deterministic GPU starvation between agents; CUDA stream contention from two inference threads. Weighed against: Option A (per-agent multi-thread sharing GPU directly) — rejected due to unpredictable serialization under load cascading into missed FSM transitions.
- (decision) AD-3 Queue drop policy: All inter-stage queues use oldest-frame eviction when full (never block the capture thread). At 10 FPS, a stale frame is worthless; blocking would cascade a single slow inference tick into a full pipeline stall. Binds: all Agent-internal pipeline queues. Prevents: cascading stall from slow GPU tick.
- (decision) AD-4 Game State ownership: Each Agent owns its own Game State exclusively. No shared Game State store. The only state that crosses agent boundaries is the Party State subset published over the Party Bus (FSM state, HP%, MP%, position, buff presence). Orchestrator receives only heartbeat signals — never reads Game State. Binds: WL Agent, PP Agent, Party Orchestrator. Prevents: shared mutable state contention; two agents writing the same Game State object.
- (decision) AD-5 Control surface: System tray app + minimal always-on-top status window (pystray + PyQt or tkinter overlay). Tray menu: start/stop session, select profile, launch recording mode. Status window: FSM state per agent, HP/MP, session timer, last log line. Recording Mode toggled via global hotkey. Shadow Mode set at launch (startup flag). No full GUI panel. Binds: UI subsystem. Prevents: heavyweight GUI surface that creates suspicious process activity; CLI-only operation that lacks live status visibility.
- (decision) AD-6 Training pipeline boundary: Separate CLI tool (python -m lagent.train). Not launched from tray app. Prevents accidental co-execution with live session (training uses 4-6GB VRAM). Runtime has no dependency on MLflow server at startup. Binds: Training Pipeline subsystem. Prevents: training deps loading into live session process.
- (decision) AD-7 Model versioning handoff: Convention-based path. Training writes validated model to fixed path (models/{class}/current.pt, models/common/current.pt) atomically via temp-write + rename. Runtime loads current.pt at session start — no MLflow query on critical path. MLflow used for training tracking only. Binds: GPU Inference Server, Training Pipeline. Prevents: runtime startup dependency on MLflow server being live.
- (decision) AD-8 Human Simulation Layer: Shared importable library (lagent.hsl) with per-agent stateful instances. Fatigue state and timing params are per-instance (per agent), not global. All action output from any agent process must pass through its local HSL instance — non-optional. Binds: WL Agent, PP Agent, all action execution paths. Prevents: two agents sharing fatigue state; HSL being bypassed by any code path.
- (decision) AD-9 Session telemetry: Single SQLite DB (sessions.db) in WAL mode. One row per session; action logs and FSM events appended per-session-id. All agent processes write to the same DB via separate connections (WAL allows concurrent writers). Binds: WL Agent, PP Agent, Orchestrator. Prevents: per-process DB files that require post-session merge to query party-wide events.
- (decision) AD-10 OCR placement: EasyOCR runs inside the GPU Inference Server alongside YOLO. Agent sends frame + named ROI crop coordinates. Server returns a single PerceptionResult (detections + OCR values). Agents have zero vision responsibility — they consume structured PerceptionResult only. Binds: GPU Inference Server API, WL Agent, PP Agent. Prevents: split perception responsibility; CPU-only OCR path adding 30-50ms to agent decision cycle.
- (decision) AD-11 ZeroMQ socket patterns: (1) Agent→GPU Server: each agent uses a dedicated DEALER socket to one ROUTER socket on the GPU server — async, non-blocking, handles batching natively. (2) Party Bus: each agent PUBs its PartyState on its own endpoint; each agent and the Orchestrator SUB to peer endpoints — fire-and-forget, no round-trip. (3) Orchestrator heartbeat: SUB-only, reads heartbeat messages published by each Agent on their PUB socket. Binds: all inter-process communication. Prevents: blocking REQ/REP on the inference path; PUB/SUB on inference (no acknowledgement); mixed socket patterns that make message routing ambiguous.
- (decision) AD-12 Dependency direction: lagent.hsl, lagent.common (shared types: GameState, PartyState, PerceptionResult, Action, AgentProfile) → imported by agents and GPU server. Agents never import from each other. GPU Inference Server never imports from Agent modules. Training pipeline (lagent.train) may import lagent.common types but nothing from runtime modules (lagent.agent, lagent.hsl). Tray/UI imports only session telemetry reader and process launcher — never agent internals. Binds: all modules. Prevents: circular imports; training deps loading into runtime; agents cross-importing.
- (decision) AD-13 Recording Mode process topology: Recording Mode runs inside the Agent process (same process as WL Agent, single-window Phase 1). A RecordingMode flag switches the capture thread to also write frames to disk and log input events via a second pynput listener. No separate recorder process. Binds: WL Agent, Recording Mode. Prevents: separate recorder process adding IPC complexity; Recording Mode interfering with live session control flow (it is mutually exclusive with live Session — you either record or run, not both simultaneously).
