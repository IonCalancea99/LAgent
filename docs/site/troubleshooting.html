Troubleshooting

These are the failure patterns observed during real setup and verification runs of this project, distilled from docs/package-restrictions.md. Most failures were environment drift, not project bugs — read the decision rule at the bottom first.

Environment discipline

Symptom externally-managed-environment, No module named pytest, No module named numpy when installing or running LAgent.

Cause: a command targeted the system/OS-managed Python instead of the project's virtual environment.

Fix:

cd /path/to/LAgent
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -U pip
python -m pip install -e .
  • Never run python3 -m pip install ... or pip install ... against the system interpreter.
  • Never pass --break-system-packages to work around the PEP 668 guard.
  • Always confirm which python resolves inside .venv before installing or testing.

Mismatched shells / interpreters

If dependency installs happen in one shell (e.g. a terminal) but tests run from another (e.g. an IDE-integrated shell), you can end up with three different Python states: system Python, the project .venv, and whatever the editor defaults to. Always run both install and test commands from the same activated .venv:

cd /path/to/LAgent
source .venv/bin/activate
PYTHONPATH=. python -m pytest -q

Platform-specific package errors

Symptom Install failures or resolution errors for pywin32, dxcam, or other Windows-only screen-capture tooling on macOS/Linux.

This is expected. pyproject.toml declares pywin32 as sys_platform == 'win32' only, and dxcam is Windows-native. Do not attempt to force-install these on a non-Windows host — they are intentionally unavailable there. Use the Docker path or the cross-platform dependency subset for development/testing on macOS/Linux.

Python runtime mismatch

The declared runtime target is Python 3.12. If your default toolchain resolves to a different version (e.g. 3.14 or an OS-managed interpreter), create the virtual environment explicitly with python3.12 rather than relying on whatever python3 happens to point to.

SSL / certificate issues reaching PyPI

Symptom Package index unreachable, SSL trust errors during pip install.

Treat this as an environment/infrastructure issue, not a project code problem. Valid fixes include using the environment's own certificate bundle, confirming the venv is active, and verifying Python/OpenSSL versions are consistent. Avoid reaching for --trusted-host or similar flags unless there is a clear, documented reason and it's explicitly approved — these can mask a real trust-chain problem.

Keep dependencies aligned to the manifest

pyproject.toml is the single source of truth for dependencies. If a local import fails, verify in this order before adding new packages ad hoc:

  1. The active interpreter is the project's .venv
  2. The project was installed via pip install -e .
  3. The missing package is part of the declared dependency set (or a test-only requirement)
  4. The package is valid for your current OS and Python version

Prefer Docker for repeatable validation

For CI-like or repeatable checks, use the project's container path instead of ad hoc local pip attempts:

docker build -t lagent-test .
docker run --rm lagent-test

Decision rule

Fix the environment first If a command fails because of a system package policy, missing interpreter alignment, an unsupported OS dependency, or SSL/certificate trust problems — stop and fix the environment before changing project code. The environment is the primary suspect for these failure classes, not the code in lagent/.
