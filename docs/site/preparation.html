Preparation & Configuration

Once the package is installed, LAgent needs a few things in place before the first session: a working directory layout, valid YAML agent profiles, and trained model weights. This page covers all of it.

Directory structure to prepare

These directories are structural seeds — they must exist even though some are excluded from source control:

LAgent/
├── data/                 # sessions.db (WAL-mode SQLite) lives here
├── recordings/           # Recording Mode output + ingested YouTube frames
├── models/
│   ├── common/current.pt   # class-agnostic YOLO model
│   ├── warlord/current.pt  # Warlord-specific YOLO model
│   └── prophet/current.pt  # Prophet-specific YOLO model
└── profiles/
    ├── fishing.yaml
    ├── warlord.yaml
    └── prophet.yaml

Create any missing directories before your first run:

macOS / Linux (bash, zsh)

mkdir -p data recordings models/common models/warlord models/prophet

Windows PowerShell

New-Item -ItemType Directory -Force data, recordings, models/common, models/warlord, models/prophet

Agent profiles (YAML)

Each character class (and the Fishing proof-of-concept) is driven entirely by a YAML profile — there is no hardcoded behavior per class. Profiles live in profiles/ and are loaded and validated by a Pydantic v2 schema (AgentProfile) at startup. The walkthrough below builds a profile field by field.

Figure 1 — the end-to-end profile creation workflow covered by Steps 1–7 below.

Profiles tune one of three fixed classes today The CLI (--class choices in lagent/agent/__main__.py), the startup resolver (SUPPORTED_PROFILES in lagent/agent/startup.py), and the tray launcher (AGENT_LAUNCH_SPECS in lagent/ui/process_manager.py) all hardcode the same three names: warlord, prophet, fishing. This guide walks through re-authoring one of those profiles (e.g. to match your own resolution, key bindings, or pacing) end to end — the YAML file alone is enough for that. Wiring up a genuinely new fourth class name also requires code changes in those three places, not just a new profile file.

1Start from the matching bundled template

Pick whichever bundled profile matches the class you're configuring and use it as your editing starting point (back it up first if you want to compare against the original):

TemplateGood fit for…
profiles/fishing.yamlA single repeating skill loop with a wait/timeout state (crafting, gathering, simple farming)
profiles/warlord.yamlMelee/DPS combat: pull → fight → loot, plus death recovery and inventory return rules
profiles/prophet.yamlSupport/buff classes: timer-driven casting with party proximity safety

macOS / Linux

cp profiles/warlord.yaml profiles/warlord.yaml.bak

Windows PowerShell

Copy-Item profiles/warlord.yaml profiles/warlord.yaml.bak

2Keep the identity field in sync

name must match both the file stem and the --class value passed on the command line — all three stay aligned since you're editing an existing supported class rather than renaming the file:

name: warlord   # profiles/warlord.yaml  ⇄  --class warlord

3Map ROIs on your screen

roi_positions is a dictionary of named pixel rectangles [x1, y1, x2, y2], measured from the top-left corner (0, 0) of the captured game window. Take a screenshot at your real play resolution, note the pixel bounds of every element the agent needs to read (HP/MP bars, buff icons, a bite or tension indicator, a mob-detection area), and record each as a rectangle.

Game window (0,0) top-left
health_bar [100,20,300,40]
mana_bar [100,45,300,65]
mob_area [300,100,1200,800]

Figure 2 — each ROI is defined by its top-left corner (x1, y1) and bottom-right corner (x2, y2); coordinates are raw capture pixels, not percentages.

roi_positions:
  health_bar: [100, 20, 300, 40]
  mana_bar: [100, 45, 300, 65]
  mob_area: [300, 100, 1200, 800]
Coordinates must fit the frame Every rectangle needs x2 > x1 and y2 > y1, non-negative values, and must fit inside your actual captured frame size — a rectangle sized for a 1920×1080 window will be rejected (or silently clipped, depending on caller) against a smaller capture. Re-measure ROIs whenever you change resolution or UI scale.

4Design the FSM before writing YAML

fsm_bindings maps each state name to its own parameter block — the next state to transition to, timeouts, and any state-specific keys or thresholds. Sketch the state cycle first; the fishing profile's loop is the simplest worked example:

IDLE
→
CASTING
→
WAITING
→
REELING
→
IDLE

Figure 3 — profiles/fishing.yaml's FSM: cast a line, wait for a tension-indicator detection (or time out back to idle), reel in, repeat.

fsm_bindings:
  IDLE:
    next: CASTING
    cast_key: "2"
    wait_timeout: 10.0
  CASTING:
    next: WAITING
    cast_duration: 0.5
  WAITING:
    next: IDLE
    wait_timeout: 10.0
    timeout_action: return_to_idle
    tension_class: tension_indicator
    tension_confidence_threshold: 0.80
  REELING:
    next: IDLE
    reel_key: "3"

Combat profiles follow the same pattern with different states — see profiles/warlord.yaml's idle → pulling → fighting → looting cycle on the Combat Mode page.

5Bind skills to keys and buff timers

skill_key_bindings maps a logical action name (referenced from fsm_bindings and the agent's policy code) to the keyboard key bound to that skill in-game. buff_timer_durations records how long each buff lasts so the agent knows when a re-cast is due:

skill_key_bindings:
  cast: "2"
  reel: "3"
buff_timer_durations:
  haste: 300.0

6Tune detection confidence and human-like timing

confidence_thresholds sets the minimum YOLO detection confidence per class name (plus a default fallback); raise a specific entry if that detector is noisy in your captures. skill_timing gives each skill a Gaussian {mean, std} keystroke delay in seconds so input timing doesn't look robotic; bezier_offset_range does the same for mouse-path curvature:

confidence_thresholds:
  default: 0.6
  tension_indicator: 0.80
bezier_offset_range: [15, 30]
skill_timing:
  default: {mean: 0.18, std: 0.05}
  cast: {mean: 0.2, std: 0.08}
  reel: {mean: 0.15, std: 0.05}

7Validate before your first run

Two ways to check a profile without launching a full session:

# Pure YAML/schema validation — no capture, no session
python3 -c "from lagent.agent.profile import load_profile; load_profile('warlord')"

# Smoke-start the agent process itself (loads and validates, then exits)
python -m lagent.agent --class warlord --check
Fail-fast, no silent fallback An invalid or incomplete profile raises a ProfileValidationError (or a Pydantic ValidationError) immediately, before any session begins — there is no runtime fallback to defaults. Fix the reported field and re-run.

Validation checks worth knowing while editing:

  • All seven required top-level fields (below) must be present.
  • Every ROI rectangle must satisfy x2 > x1 and y2 > y1, with non-negative coordinates, and must fit inside the actual captured frame's width/height.
  • confidence_thresholds values must be between 0.0 and 1.0.

Required top-level fields (enforced by lagent.agent.profile):

FieldPurposeStep
nameProfile identifier (e.g. fishing, warlord, prophet)2
roi_positionsNamed regions of interest as [x1, y1, x2, y2] pixel rectangles (HP bar, MP bar, buff icons, etc.)3
fsm_bindingsFSM state transitions, timeouts, and per-state behavior parameters4
skill_key_bindingsLogical action name → keyboard key mapping5
buff_timer_durationsSeconds each buff lasts, used to schedule re-casts5
confidence_thresholdsPer-class YOLO detection confidence cutoffs (plus a default)6
skill_timingPer-skill Gaussian {mean, std} timing used for human-like keystroke delays6

Full bundled example — profiles/fishing.yaml with every field from the steps above assembled into one file:

name: fishing
roi_positions:
  health_bar: [100, 20, 300, 40]
  mana_bar: [100, 45, 300, 65]
  bite_indicator: [500, 300, 600, 400]
fsm_bindings:
  IDLE:
    next: CASTING
    cast_key: "2"
    wait_timeout: 10.0
  CASTING:
    next: WAITING
    cast_duration: 0.5
  WAITING:
    next: IDLE
    wait_timeout: 10.0
    timeout_action: return_to_idle
    tension_class: tension_indicator
    tension_confidence_threshold: 0.80
  REELING:
    next: IDLE
    reel_key: "3"
skill_key_bindings:
  cast: "2"
  reel: "3"
buff_timer_durations:
  haste: 300.0
confidence_thresholds:
  default: 0.6
  tension_indicator: 0.80
bezier_offset_range: [15, 30]
skill_timing:
  default: {mean: 0.18, std: 0.05}
  cast: {mean: 0.2, std: 0.08}
  reel: {mean: 0.15, std: 0.05}
enable_ocr: true
enable_recording: false
fatigue_interval: [1800.0, 3600.0]

Combat classes add a couple of optional blocks on top of the required fields: recovery (death recovery action sequence) and inventory (town-return / deposit / drop rules) — see profiles/warlord.yaml and the Combat Mode page for a worked example. Leave them empty (as in profiles/fishing.yaml) if your class doesn't need them.

Mode flags enable_ocr (default true) and enable_recording (default false) toggle OCR text extraction and the recording hook for this profile.

Sessions database

All processes (agents, orchestrator, UI) append events to a single WAL-mode SQLite database at data/sessions.db, each from its own connection:

  • sessions(session_id, started_at, profile, mode)
  • events(id, session_id, ts, source, type, payload_json)

The database file is created automatically on first run as long as the parent data/ directory exists — no manual schema setup is required.

Model files

The GPU Inference Server loads YOLO weights from models/<class>/current.pt once at startup (no in-session reload). Two ways to get a current.pt in place:

  1. Bring your own weights — place a compatible .pt file at models/common/current.pt, models/warlord/current.pt, and/or models/prophet/current.pt.
  2. Train your own — follow the Training Pipeline guide (record → prelabel → train); the pipeline writes current.pt atomically via a temp-write + os.replace() once a model passes its mAP threshold.
No model file yet? A session can still be started for development/debugging purposes, but real detection and OCR quality depend entirely on having a trained current.pt per class.

Pre-flight checklist

  • Virtual environment created and package installed (see Installation)
  • data/, recordings/, and models/<class>/ directories exist
  • profiles/<class>.yaml exists and passes validation for every class you plan to run
  • ROI pixel coordinates in each profile match your actual game window resolution/layout
  • models/<class>/current.pt is present for every class you plan to run
  • No training run is active on the same machine (GPU must be free for the live session)
  • Game client window is open and titled as expected (default: Lineage II)
