Label Studio Guide

This page is the operational companion to the Training Pipeline. Use it when creating a Label Studio project, checking that every required label is present, and preparing corrected annotations for YOLO training.

The label names are part of the model contract Label values are case-sensitive. Create only the labels listed for the model family, keep their spelling unchanged, and train one model family at a time. A missing or inconsistent label can make a model appear to train successfully while producing unusable detections.

Recommended workflow

1. Record or ingest frames
→
2. Run YOLO prelabel
→
3. Import tasks
→
4. Correct every frame
→
5. Export and normalize
→
6. Train
  1. Stop any live session before running training or GPU-heavy prelabeling.
  2. Run python -m lagent.train prelabel --recording recordings/<session-folder> to create Label Studio prediction suggestions in prelabeled.json.
  3. Create a Label Studio project with the exact template for the model family below, then import prelabeled.json. If prelabeling is unavailable, create tasks from the recording frames using the procedure in Training Pipeline: import frames.
  4. Correct every submitted frame, including frames with no objects. Empty frames are valid negative examples.
  5. Export raw Label Studio JSON and normalize it to labels.json before training. Keep coordinates as percentages; the trainer converts them to YOLO coordinates.

Install and create the project

Label Studio runs as a separate local application. It is intentionally not installed as a LAgent runtime dependency.

python3.12 -m venv .label-studio-venv
source .label-studio-venv/bin/activate
python -m pip install -U pip label-studio
LABEL_STUDIO_LOCAL_FILES_SERVING_ENABLED=true \
LABEL_STUDIO_LOCAL_FILES_DOCUMENT_ROOT="$PWD/recordings" \
label-studio start

Open http://localhost:8080, create a project, choose Labeling Setup → Custom Template, paste exactly one template below, and save it before importing tasks. Replace no label values unless the corresponding model code and training data are changed together.

How many images to label

Counts below are planning heuristics per model family, not validated minimums or a guarantee of model quality. They assume varied screenshots sampled across gameplay states. More frames may be needed when objects are small, occluded, rare, or visually different across zones; use held-out validation results to decide whether to collect more data.

Model familySuggested starting setRecommended first setPer-label target
common1,000 images3,000–5,000300–500 positive images per label, plus 10–20% true negatives
warlord800 images2,000–4,000500+ mob positives; 200+ melee_range positives if used
prophet800 images2,000–4,000400+ positives each for mob and character
fishing500 images1,500–3,000500+ tension_indicator positives across all visual states

These are starting targets, not a guarantee of quality. A rare class is better represented by 500 varied positive examples than by 5,000 near-identical screenshots. Hold out at least 20% of the frames for validation, and make sure both early and late portions of the recording contain useful examples because the split is deterministic.

Common model template

Use this model for shared scene understanding. Label the controlled character, targetable mobs, visible loot, and the complete death-state indicator.

<View>
  <Image name="image" value="$image" zoom="true" zoomControl="true"/>
  <RectangleLabels name="tag" toName="image" strokeWidth="2">
    <Label value="mob" background="#D55E00"/>
    <Label value="character" background="#0072B2"/>
    <Label value="loot" background="#009E73"/>
    <Label value="death_screen" background="#CC79A7"/>
  </RectangleLabels>
</View>
LabelDraw the box aroundDo not label
mobEach targetable hostile instanceNames, damage text, or decorative effects
characterThe controlled character's visible bodyParty members unless they are the controlled character
lootEach visible loot object relevant to pickupGround texture or floating text
death_screenThe stable death panel or indicatorTemporary red flashes or unrelated UI

Warlord model template

Use this model for combat targeting. melee_range is optional: configure it only when the game provides a stable visible range indicator. Otherwise range is derived from mob and character boxes.

<View>
  <Image name="image" value="$image" zoom="true" zoomControl="true"/>
  <RectangleLabels name="tag" toName="image" strokeWidth="2">
    <Label value="mob" background="#D55E00"/>
    <Label value="melee_range" background="#F0E442"/>
  </RectangleLabels>
</View>
  • Label every targetable hostile separately, including partially occluded hostiles when the identity and useful extent are clear.
  • Use melee_range only for the same visual indicator in every frame. Do not invent a box to represent an inferred distance.
  • Include idle, approaching, attacking, crowded, and empty combat scenes.

Prophet model template

Use this model for buff-safety perception and the distance reference to the controlled character.

<View>
  <Image name="image" value="$image" zoom="true" zoomControl="true"/>
  <RectangleLabels name="tag" toName="image" strokeWidth="2">
    <Label value="mob" background="#D55E00"/>
    <Label value="character" background="#0072B2"/>
  </RectangleLabels>
</View>
  • Label the controlled character consistently, even when only part of the body is visible.
  • Label every nearby hostile relevant to the buff safety decision, not only the current target.
  • Include safe scenes, unsafe scenes, crowded scenes, and scenes where the character is absent.

Fishing model template

Use this model for the changing filled fish-HP segment while the fishing FSM is waiting.

<View>
  <Image name="image" value="$image" zoom="true" zoomControl="true"/>
  <RectangleLabels name="tag" toName="image" strokeWidth="2">
    <Label value="tension_indicator" background="#009E73"/>
  </RectangleLabels>
</View>
  • Box only the filled fish-HP segment. Do not include the complete static gauge frame or empty track.
  • Include the filled segment at low, medium, and high widths so its bounding-box width tracks fish HP.
  • Include empty frames for waiting states where no tension indicator is visible.

Labeling quality check

Before exporting, verify each item below for every model family:

  • Every task is submitted; no task remains a draft.
  • Every visible in-scope object has exactly one appropriate box, and each object instance has its own box.
  • True negative frames are empty; do not draw a full-frame box for “none.”
  • Boxes stay within the image and have non-zero width and height.
  • Label spelling and capitalization exactly match the selected template.
  • Examples cover different maps, backgrounds, scales, animation states, occlusion, and screen positions.
  • Near-duplicate frames do not dominate the dataset.
  • The rarest label meets its target before training begins.

Export and prepare training input

  1. Choose Export → JSON in Label Studio. Do not use COCO, YOLO, JSON-MIN, or predictions-only output.
  2. Save the export as label-studio-export.json in the recording directory.
  3. Run the normalization snippet in Training Pipeline: export and normalize.
  4. Confirm that labels.json contains {"tasks": [...]}, every task points to a filename under frames/, and each rectangle result has type rectanglelabels.
  5. Run python -m lagent.train train --recording recordings/<session-folder> --model-class <family>.
Review predictions before training prelabeled.json contains prediction suggestions, not reviewed annotations. Correct and submit every task before exporting; the trainer consumes the submitted annotations, not predictions alone. Raw Label Studio exports are accepted directly, or you can normalize them to labels.json as described in the training guide.
